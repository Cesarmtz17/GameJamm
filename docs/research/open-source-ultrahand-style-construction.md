# Keep the sockets, rebuild the joints

The only public open-source project found that does socket-based part fusing for a physics builder is **ComponentFuseMechanic**, an MIT-licensed Unreal Engine 5.2 prototype by Evelyn Schwab ([repo](https://github.com/EvelynSchwab/ComponentFuseMechanic)). No open repo in UE, Godot, or Unity does player-built part joining with sockets, detach, and clipping checks end to end, so the prototype cannot be bought off the shelf. The repo's socket search and candidate selection are worth keeping under MIT with attribution. Its per-tick break-and-recreate constraint loop, its target physics-off fallback, and its sweep-based detach are not worth keeping, and four small bugs need fixing before anything else. For a UE 5.8 jam prototype, the recommended shape is sockets as authored anchor geometry, a small typed joint graph as the source of truth, and Chaos constraints created once from that graph. The project's README targets UE 5.2 and the repo's `.uproject` says `EngineAssociation: 5.2` (repo `Fuse.uproject`), so a 5.8 migration and compile pass come first. Nothing in this report was verified against 5.8 headers. The legal path is clean for the code (MIT is a one-condition license), but the bundled Epic character and Caleb Longmire/ALS animation assets need their own license checks before they ship. Official jam rules were not readable; the key sourced-asset clause was seen only through a forum excerpt.

## Sockets are cheap to author but cannot carry the rules

ComponentFuseMechanic treats a socket as a joint by name alone. `IsComponentFusable` and the pair search test `Contains("Attach")` or the `FusableSocketSubName` property, so any socket with that substring is a joint, with no axis, type, or compatibility metadata (repo `FFuseComponent.cpp:137, 380, 384`). That is the cheapest possible architecture: it needs no data model and the anchors live in the DCC asset. The cost shows up in four places. Validation happens only at pick time, through one overlap query (line 404), and at detach time, through a sphere sweep (line 658); there is no persistent structure to check for cycles, orphan parts, or illegal joint pairings. Detach re-discovers constraints by sweeping nearby actors and walking `GetAttachedActors`, which the repo's own comment calls "Not an ideal solution" (lines 640-641). Connectivity is whatever the Chaos constraint says it is, so any engine break or reset leaks straight into game state. And there is no replication code at all; all joint breaking and re-creation runs per tick on the local client.

A parts-graph with typed joints inverts those trade-offs. Nodes are parts with stable IDs, and edges are joint records carrying a type, anchor transforms in each part's local space, limits, and compatibility tags. Validation becomes a graph check that needs no physics, detach becomes an edge removal, and networking can replicate the graph and rebuild constraints locally. The price is an authoring step for each joint anchor and a data layer that the socket design avoids. For LLM-generated specs the difference is sharp: a parts-and-joints JSON can be validated against a schema and rejected before any physics runs, while a socket-only build has no spec format at all. I found no public source that compares these two designs for physics builders, so this comparison is design reasoning, not a sourced finding. The hybrid I would pick keeps sockets as anchor geometry and makes the graph the only authority on connectivity.

## Version risk sits in the Chaos loop, not the signatures

The engine calls the repo uses (sweeps, overlaps, sockets, `AttachToComponent`, constraints, `SetWorldLocationAndRotation`) are long-standing, and I could not confirm any signature change for 5.8 because the 5.8 API pages returned only tables of contents. The 5.8 release notes, seen only through search excerpts, describe Chaos Core work for "more responsive and scalable simulation" and a unified Enhanced Input with Common UI ([UE 5.8 release notes](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5-8-release-notes)). Those changes are **single-source**, and I could not confirm whether any of them touches the fuse path. The larger risk is behavioral. The fuse loop breaks and re-creates the constraint on every tick until the interp finishes (`FFuseComponent.cpp:600-613`), so it depends on Chaos constraint behavior that has a history of trouble: a UE 5.0.2 report says the constraint "broken" event sometimes did not fire ([forum](https://forums.unrealengine.com/t/5-0-2-chaos-bug-physics-constraint-broken-event-not-firing/594556)), and an Epic tracker entry says enabling plasticity on a Chaos joint zeroes the drive target at init, with status in 5.8 unverified ([UE-368639](https://issues.unrealengine.com/issue/UE-368639)). A forum user reported that a simulated object snapped back to its old location after re-enabling physics, with `TeleportPhysics` suggested over `ResetPhysics` as a workaround ([forum](https://forums.unrealengine.com/t/physic-simulated-object-snaps-back-to-old-location-after-re-enabling-simulated-physics/2658764)). All three are single-source and anecdotal. The repo calls `ResetPhysics` at lines 575 and 606, so the snap-back question is the one to test first in 5.8.

## Five code defects, and why the loop matters more

I read the cited code in the local clone and confirmed each defect below. Two of them, the `IsFusing` precedence and the hardcoded `"Attach"`, are small. The null dereference and the self-rejection can break gameplay, and the per-tick loop is the design problem that no one-line fix removes.

**Null dereference in `ReleaseComponent`.** Line 43 calls `GetGrabbedComponent()->SetRenderCustomDepth(false)` with no null check. `TryFuseObjects` calls `ReleaseComponent()` at lines 547 and 553 without checking that something is held, and the function reads `GetGrabbedComponent()` at line 547 without a guard. My reading is that calling fuse with nothing held reaches line 43 with a null pointer, but I did not reproduce it in the editor, and the trigger conditions depend on how `bHasValidFuse` survives between calls. Fix it once in `ReleaseComponent` with a guard, which covers every caller.

**Hardcoded `"Attach"` string.** `IsComponentFusable` at line 137 tests `SocketName.ToString().Contains("Attach")` while the pair search at lines 380 and 384 uses `FusableSocketSubName`. Changing the property therefore changes the search but not the held-object check. The commented-out block at line 416 also hardcodes the string, but it is inactive. Route line 137 through the property.

**`IsFusing` precedence.** Line 218 reads `return !CurrentFuserState == FSTATE_NONE;`. With an unscoped `UENUM` (the header declares `enum EFuserState`) and `FSTATE_NONE` equal to 0, the expression evaluates correctly by accident: the logical not yields 0 for any non-NONE state, which compares equal to `FSTATE_NONE`. The fix is `CurrentFuserState != FSTATE_NONE`. This is my reading of C++ precedence and integer promotion, not a compiled test.

**`TryDetachGrabbedComponent` always returns false.** The function breaks and destroys matching constraint actors (within lines 638-696) and then returns `false` on line 695 regardless. Callers were not checked, so the actual impact depends on whether they use the return value. Return `true` when any constraint was removed.

**Possible self-rejection in `ComponentOverlapMulti`.** Line 404 passes `GetGrabbedComponent()` as the query component and ignores only that component (line 400). The target component is not ignored, and the query uses `ECC_PhysicsBody`, so at the ideal socket-contact pose the target can overlap the held part and reject every candidate. The original logic, now commented out at lines 410-424, rejected only overlaps with components that had "Attach" sockets, which is a different rule. Whether the contact pose actually overlaps depends on mesh geometry. This is an inference from the code and needs an editor check with `f.drawdebugfuser 1`, which draws red and blue capsules for rejected and accepted candidates.

Two more items are worth fixing but are judgment calls. The interp-complete test uses `FQuat::Equals` with tolerance 0.2 (line 580), which is loose, and the supplementary sockets use a 5.0-unit tolerance (line 469), which is not in the same units as the 0.5 location test. The bigger issue is the loop itself. Lines 600-613 break the constraint, turn off simulation on the source, teleport it with `ResetPhysics`, and re-create the constraint every tick until the interp ends. Line 617 turns off simulation on the target once the 1.5-second interp window passes, which the repo calls a way to "avoid particularly bad physics clipping issues" (lines 560-565 comment that this is "a fairly unpleasant solution"). That fallback stops a held target from simulating, which is the likely source of the clipping the repo was fighting.

## Licensing: MIT is easy, the bundled assets are not

ComponentFuseMechanic's LICENSE is MIT, and its single condition is that the copyright notice and permission notice appear in all copies or substantial portions ([OSI, MIT](https://opensource.org/license/mit)). Reusing the code means keeping the LICENSE file and the notice, and the repo's `e26604e` commit already has the license in place. Two gaps remain. First, MIT covers the code, and the repo's README credits "Props" to Evelyn Schwab without a separate license, so whether the prop assets are covered by the MIT grant is an open question; treat them as needing their own permission. Second, the README lists third-party sources for the character (Epic's third-person template) and movement animations (Caleb Longmire, ALS). The repo's `Content/ThirdPerson` folder is present locally, and the only license file in the repo is the root `LICENSE`, so those assets are not covered by it. I did not verify the Epic template's terms or the Caleb Longmire and ALS licenses. Replace them or confirm them before the jam build ships.

The idea/expression line is the other risk. US law excludes "any idea, procedure, process, system, method of operation" from copyright ([17 U.S.C. §102(b) as discussed by Samuelson](https://www.law.berkeley.edu/center-article/why-copyright-law-excludes-systems-and-processes-from-the-scope-of-its-protection/)), in line with Baker v. Selden ([Lexplug](https://www.lexplug.com/casebrief/baker_v_selden_65bd562dabbe1c5b9f8a38dd)). A "fuse two parts at sockets, check clipping, detach" mechanic is therefore an idea that can be reimplemented from its public description. Copying the repo's classes, function names, or assets is copying the expression, which MIT governs. The line is not always clear, and close structural copies can still count, so a rewrite that follows the description and not the code is the safer route. On the other side of the boundary, extracting or decompiling a commercial game such as Tears of the Kingdom is not acceptable. US law restricts circumventing access controls ([17 U.S.C. §1201(a)(1)(A)](https://www.law.cornell.edu/uscode/text/17/1201)), and §1201(f) interoperability is narrow. Nintendo's account terms prohibit reverse engineering and decompilation of the services ([Nintendo Life, 2025](https://www.nintendolife.com/news/2025/05/nintendo-updates-its-user-agreement-to-crack-down-on-emulation)). This report and the prototype use only the public design description, never extracted code or assets.

Finally, the jam rules were not fully readable. The Epic AI MegaJam official rules (Box) were not accessible; a forum post quotes Section 15(c) as allowing sourced, non-original assets if they are declared at submission, and that the entrant has the rights to use them ([forum excerpt](https://forums.unrealengine.com/t/what-is-unclear-to-me-is-the-expected-form-and-timing-of-the-proof-of-authorization-license/2849537)). That is single-source and truncated, so read the official text before submitting. The Unreal EULA and Fab terms returned HTTP 403 and were not read.

## Recommendation: adopt the sockets, rebuild the loop

Adopt the socket naming search and sphere-sweep candidate selection (`FFuseComponent.cpp` around lines 370-420) as is under MIT, keeping the LICENSE file and the copyright line, and mark modified files as modified, which is the practice Apache-2.0 would require and is cheap to follow here. Fix the four small defects first: add the null guard in `ReleaseComponent` and `TryFuseObjects`, change `IsFusing` to `!=`, route `IsComponentFusable` through `FusableSocketSubName`, and make `TryDetachGrabbedComponent` return true when it removes a constraint. Then fix the self-rejection by ignoring the target component's pair in the overlap, or by checking only the grabbed component against non-target bodies.

Rebuild the fuse loop. Replace the per-tick break-and-recreate with a single kinematic or physics-off move to the ideal transform, then create one constraint at the end, and drop the target physics-off fallback. Keep `ResetPhysics` only as the 10-second failsafe, and log when it triggers. Introduce a small joint graph as the source of truth, so that detach is an edge removal and not a sweep, and so that LLM-generated part specs can be validated as JSON before any physics runs. This is the one piece that costs real effort, and it is the one piece I would not copy from the repo.

Treat the following as out of scope for the jam prototype: the three-capture orthographic projection system, which the README itself calls "not ideal"; replication; a full Blueprint migration; the L_Fuse_TestMap content; and LLM spec ingestion beyond schema validation. Replace the Epic character and the Caleb Longmire/ALS animations with assets whose licenses are confirmed, or with a placeholder, before the build.

No UE 5.8 API signature was confirmed from a web source; the 5.8 reference pages returned tables of contents only. The compile-level claim that the code builds on 5.8 is untested, as is the claim that `ResetPhysics` snap-back is fixed or unfixed in 5.8. No open repo was found that does player-built part joining with sockets in UE, Godot, or Unity, so the comparison of socket and graph designs is design reasoning, not sourced. ## Conclusion

The useful finding is narrower than "reuse ComponentFuseMechanic." Its socket search is a small, MIT-licensed, working idea of how to pick anchors from mesh sockets, and that part is worth taking. The part that would fail in a real build is the joining loop, which mixes engine constraints with per-tick teleports and makes the physics engine the only source of truth for what is connected. The prototype should therefore treat connectivity as data, with sockets as the geometry and constraints as an output, which also makes LLM-generated specs checkable before any physics runs.

The legal exposure is also more concentrated than the code suggests. MIT is one condition, and the project's own code can be reused with a notice. The risk is in the bundled assets and in any attempt to reproduce a commercial game's internals, which this work does not do. Before a 5.8 build, confirm the Epic template, Caleb Longmire, ALS, and prop licenses, read the official jam rules directly, and run the self-rejection and null-guard checks in the editor, because those two are the defects most likely to change what the prototype does in play.
